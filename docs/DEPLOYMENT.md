# Deployment

## Go live for free (Render + Neon + Brevo + UptimeRobot)

This setup runs the public beta for ₹0/month on a free subdomain such as `https://finsight-ai.onrender.com`. It takes about 30 minutes. Do the steps in order, because each one produces a value the next one needs.

| Service | What it does | Free tier |
| --- | --- | --- |
| [Render](https://render.com) | Runs the Docker container (API + web app) with HTTPS | 1 web service, 512 MB RAM, sleeps after 15 min idle |
| [Neon](https://neon.tech) | Managed PostgreSQL database with backups | 0.5 GB storage, does not expire |
| [Brevo](https://www.brevo.com) | Sends password-reset emails over SMTP | 300 emails/day |
| [UptimeRobot](https://uptimerobot.com) | Pings the app so it stays awake, and alerts you if it goes down | 50 monitors, 5-minute checks |

### 1. Create the database (Neon)

1. Sign up at Neon and create a project. Pick the region closest to your users (for example AWS Singapore).
2. On the project dashboard, copy the **connection string**. It looks like `postgresql://user:password@ep-xxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`.
3. Keep it private: it contains the database password. The app accepts it as-is and switches it to the installed psycopg 3 driver automatically.

### 2. Set up email (Brevo)

1. Sign up at Brevo, open **Senders, Domains & Dedicated IPs → Senders**, and add and verify the address that emails should come from (for example your Gmail).
2. Open **SMTP & API → SMTP** and note the **login** and create an **SMTP key**.
3. Without your own domain, some emails may land in spam. Adding a custom domain later fixes this; no code change is needed.

### 3. Deploy the app (Render)

1. Sign up at Render with your GitHub account and allow access to the `FinSight_AI` repository.
2. Choose **New → Blueprint** and select the repository. Render reads [`render.yaml`](../render.yaml).
3. When asked for the values marked `sync: false`, enter:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | The Neon connection string from step 1 |
   | `PUBLIC_APP_URL` | `https://<service-name>.onrender.com` (shown on the service page; update it after the first deploy if needed) |
   | `SUPPORT_EMAIL` | The address shown on the Privacy and Terms pages. Leave it empty to link to GitHub Issues instead |
   | `SMTP_USER` | Brevo SMTP login |
   | `SMTP_PASSWORD` | Brevo SMTP key |
   | `MAIL_FROM` | `FinSight AI <your-verified-sender@gmail.com>` |

   `SECRET_KEY` is generated by Render automatically. Never commit any of these values; the repository is public.
4. Click **Apply**. The first build takes about 5–8 minutes. When the service shows **Live**, open the URL.

On startup the app applies database migrations and creates the demo account. Every push to `main` redeploys automatically.

### 4. Keep it awake (UptimeRobot)

Render's free tier sleeps after 15 minutes without traffic, and the next visitor then waits 30–50 seconds. To prevent this:

1. Sign up at UptimeRobot and add an **HTTP(s)** monitor for `https://<service-name>.onrender.com/api/health` every **5 minutes**.
2. Add your email as an alert contact so you hear about outages.

One always-on service uses about 730 of Render's 750 free instance hours per month.

### 5. Check the live site

- `https://<service-name>.onrender.com/api/health` returns `"status":"ok"` and `"database":"postgresql"`.
- Create an account (the consent box is required), add a transaction, sign out, and sign back in.
- Use **Forgot password?** with your own email. The reset email arrives, and the link sets a new password.
- **Explore the live demo** opens the fictional workspace. It is restored to its original data every night at 03:00 IST.
- In the browser's developer tools, the `finsight_session` cookie is marked `Secure` and `HttpOnly`.
- `/api/docs` returns 404. Set `ENABLE_API_DOCS=true` only if you want the API reference public.

### Costs and limits to know

- **Database:** 0.5 GB on Neon's free tier holds thousands of users' ledgers. Neon keeps a short point-in-time restore window; users can always export their own CSV.
- **One instance:** in-memory sign-in rate limits reset on each deploy. That's acceptable for a beta; move them to Redis or PostgreSQL before running more than one instance.
- **Upgrading:** when you need no sleep and more memory, switch the Render service to the Starter plan (about $7/month). Nothing else changes.
- **Custom domain:** add it under the Render service's **Settings → Custom Domains** (HTTPS is automatic), then update `PUBLIC_APP_URL`.

## Recommended shape

Build the SPA once and serve it from FastAPI behind an HTTPS reverse proxy. This keeps the session cookie same-origin and avoids CORS complexity.

```powershell
cd frontend
npm ci
npm run build
cd ..\backend
.\.venv\Scripts\python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

FastAPI detects `frontend/dist/index.html` at startup and serves the SPA, assets, and `/api/*` from one origin. Startup-time detection means the server must start (or restart) after the build exists.

Health check: `GET /api/health` checks the database and reports the AI provider, configuration state, and version.

## Production environment

Start from [`backend/.env.example`](../backend/.env.example). At minimum:

```dotenv
ENVIRONMENT=production
SECRET_KEY=<long-random-secret>
COOKIE_SECURE=true
CORS_ORIGINS=https://finance.example.com
AUTH_RATE_LIMIT_ATTEMPTS=20
AUTH_RATE_LIMIT_WINDOW_SECONDS=300
DATABASE_URL=postgresql+psycopg://finsight:<password>@db:5432/finsight
SEED_DEMO_ON_STARTUP=false
ENABLE_SCHEDULER=true
```

Notes:

- Terminate TLS at the proxy and forward to Uvicorn on loopback.
- Use a unique, randomly generated `SECRET_KEY`; changing it invalidates existing sessions.
- Keep `COOKIE_SECURE=true` in HTTPS deployments. Production mode also enables
  secure cookies automatically.
- Authentication rate limits are stored in process memory. With multiple
  workers, use a shared rate-limit store at the proxy or replace the limiter.
- If frontend and API are separate origins, set `CORS_ORIGINS` exactly and build the frontend with `VITE_API_URL=https://api.example.com/api`. Prefer same-origin or a path-based reverse proxy because the session cookie is SameSite=Lax.
- The demo account is publicly accessible by design. Disable or restrict it if the application should not expose fictional demo data.
- No email or SMS delivery exists. Bill reminders and notifications stay in-app.

## Database

### PostgreSQL

1. Create the database and user.
2. Set `DATABASE_URL` as shown above.
3. Run migrations from `backend`:

```powershell
.\.venv\Scripts\alembic upgrade head
```

Startup applies migrations automatically (`AUTO_CREATE_TABLES=true`, the default), including databases created before migrations were tracked. Set it to `false` only if your release pipeline runs `alembic upgrade head` itself. SQLite remains the zero-setup local default.

### SQLite

The default database is `backend/data/finsight.db`. It is created and seeded on first start. Do not run multiple application instances against the same SQLite file. Back up the file if the demo data matters; it is excluded from git by default.

## Scheduler

APScheduler runs inside the API process. With one worker, the default configuration is sufficient.

With multiple workers, enable the scheduler in exactly one process (for example, a dedicated worker with `ENABLE_SCHEDULER=true`) and set `ENABLE_SCHEDULER=false` everywhere else. Running it in every worker duplicates evaluation work.

## AI provider

The default `AI_PROVIDER=deterministic` is self-contained. For an OpenAI-compatible endpoint:

```dotenv
AI_PROVIDER=openai
AI_BASE_URL=https://api.openai.com/v1
AI_API_KEY=<secret>
AI_MODEL=gpt-4o-mini
```

The backend sends it the constructed financial context. Review the provider's retention and data-processing terms before enabling it for real user data. Provider failures fall back to the deterministic grounded answer and are surfaced in the response metadata.

## PWA and caching

- The production build generates `manifest.webmanifest`, `sw.js`, and Workbox assets.
- Installability and service workers require HTTPS, except on localhost.
- API requests are network-only; the app shell is precached.
- The service worker uses automatic updates. Publish a fresh build rather than editing files in `dist`.

## Release checks

```powershell
cd backend
.\.venv\Scripts\python -m pytest -q

cd ..\frontend
npm ci
npm run typecheck
npm run lint
npm run build
npm audit --omit=dev
```

Then start the production server and verify:

- `/api/health` returns `status: ok`.
- Sign-in and demo sign-in work with secure cookies over HTTPS.
- A create/delete cycle works for a transaction, budget, goal, bill, and research run.
- Session cookies are `HttpOnly` and `Secure`.
- `/api/docs` returns 404 (hidden in production unless `ENABLE_API_DOCS=true`).
- Backups and database migrations are owned by the deployment pipeline.
